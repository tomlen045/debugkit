# fix（修复与回归）

## 前置检查（全过才许动代码）

- [ ] 至少一个 hypothesis 是 `confirmed` 且挂着决定性证据 id
- [ ] 修复方案一句话能说清："改〈什么〉，因为〈confirmed 假设〉（证据 E<n>）"
- [ ] 有 open/verifying 案卷；无案卷 → 回去立案（禁止无案修复）

## 修复动作

1. 向用户报方案：`按 H<n>（E<m>）修复：〈一句话方案〉`——除非用户已明确授权，等确认再动手。
2. 最小改动原则：只改与 confirmed 假设直接相关的代码；顺手看到的别的问题 → **另立新案**，不混修（铁律 2）。
3. 改完立即跑 `repro.cmd`——这是结案的门票，不是可选项：
   - 复现脚本转绿 → 证据入库（`fix.verify` 写 cmd/output/ts），status → verifying
   - 脚本仍然红 → **假设判错了**，修复回滚（`git checkout -- <file>` 级别的精确回滚，禁 `reset --hard`，见硬规则沿用 taskflow 禁令），hypothesis 改判 ruled_out（挂新证据），回到取证
4. **回归体检**：跑与改动相关的既有测试；没有测试的文件，补一个最小回归用例（用复现脚本改写成测试，防复发有实体）。
5. 输出：`已修复 〈case-id〉：〈方案一句话〉，复现脚本 〈N/N〉 通过 → 等你实测确认`。

## verify 段（等用户实测）

- status=verifying 期间**冻结**该案其他修复动作（不许"再顺手优化一下"——验证期改动会污染归因）
- 用户回"好了" → 走 close（fix.verify.userConfirmed=true）
- 用户回"没好/又出现了" → 修复宣告作废：verify 条目原样保留（错误结论也是证据），回取证；若已 close，走复发流程

## 复发特别程序（reopened 案卷）

1. **先写复盘再动代码**（硬规则 4）：`templates/regression-postmortem.md` 回答三问——当时的根因结论错在哪？修复为什么没盖住？验证为什么没拦住（复现脚本缺口？测试没覆盖？）？
2. 复盘结论决定路线：
   - 当时根因就找错 → 旧 hypotheses 全部重审，当新案办（保留 reopenHistory 脉络）
   - 修复被回退/被覆盖 → 查 git blame 谁动的，补护栏（测试/CI 检查）
   - 条件漏了（只在生产/特定数据出现）→ 扩复现脚本覆盖该条件，再谈修复
3. 复发 ≥2 的案卷，`knowledge.md` 强制沉淀一条根因模式（什么类型的 bug、当初为什么没抓到、下次先查什么）。
