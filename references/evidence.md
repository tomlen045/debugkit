# evidence（取证与假设）

## 取证管道（每条证据都走这一遍）

1. **设计取证命令**：针对当前疑点，选最小、最快、输出最能定生死的一条命令（日志 grep / 单点 curl / 单测 / db 查询 / `git log -p <file>`）。
2. **实跑**：把命令和关键输出原样记录——`evidence[]` 追加 `{id: E<n+1>, kind, cmd, output, digest}`；长输出落盘 `cases/<id>/artifacts/` 并在 output 里存相对路径。
3. **判读**：这条证据支持谁、排除谁？明确写进 digest（"支持 H1：错误堆栈全部来自 AuthFilter"）。
4. **更新假设表**：
   - 支持某假设 → 该假设 status 仍 open，digest 里记"支持"（升 confirmed 需要决定性证据）
   - 决定性证据 → hypothesis.status = confirmed / ruled_out，**必须挂本证据 id**（不变量 D2）
5. **向用户报一句**：`E<n>：〈digest〉 → 〈H几 支持/排除/确认〉`。

## 假设纪律

- **假设必须先入表再改代码**（硬规则 2）。入表 = 向用户复述假设 + 打算怎么验证它，用户点头才写进 hypotheses[]（高影响门槛）。
- **一次主攻一个假设**，其余标 open 排队——多线并发取证是"看起来在努力"的经典姿势。
- **排除要证据，不要直觉**："我觉得不是数据库" 不算 ruled_out；`db ping 正常 + 连接池监控无耗尽`（E2）才算。
- 假设被 ruled_out 后**不要删**——排除项是案卷最值钱的部分（下次别人就不用再查一遍），也进 findings.md 复用层。

## 三板斧优先级（取证顺序）

1. **报错原文**——堆栈第一行指向的文件:行号，先去现场再看别的
2. **最近改动**——`git log --oneline -10` + `git diff` 症状出现时间点附近的提交（"上周还好"类案件 90% 在这里结案）
3. **最小复现**——把"偶发/线上才有"变成"本地必现"是破案分水岭；复现率数据本身是证据（"5次1次500" vs "必现" 指向不同病灶）

## 环境证据（偶发案件必收）

偶发 bug 三问，答案各存一条证据：依赖版本变了吗（`git diff package.lock` / pip freeze 对比）？数据变了吗（坏样本存 artifacts/）？负载/时序相关吗（单线程跑还复现吗）？
